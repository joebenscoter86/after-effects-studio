## What the plugin does

After Effects Studio lets a creator direct an agent to create, inspect, revise and render editable motion graphics in the user's local Adobe After Effects project. The user supplies the subject and style. The plugin bundles three skills and a 19-resource motion library with the local controller. Adobe After Effects and Node.js 24+ are prerequisites. The production-derived craft guidance is self-contained; ordinary use does not require Joe's private Content repository, a personal rig, private media, or a paid asset service.

## Current execution model

The installable plugin declares a local MCP process in `.mcp.json`: `node ${PLUGIN_ROOT}/scripts/start.mjs`. The bundled Node server uses MCP stdio and communicates with AE through local file IPC and OS scripting (`osascript`/DoScript on macOS; `AfterFX.exe -r` on Windows). It does not expose an HTTP listener or call a hosted controller. The AE project and render outputs remain on the user's machine unless the user separately chooses to share an artifact through their agent host. The agent host necessarily receives tool inputs/results and may display inspected project metadata or rendered previews; its own data-handling terms are separate from this plugin's local transport.

The controller can create, mutate and delete project content. `eval.run` custom scripting is enabled by default; `AE_MCP_ENABLE_EVAL=0` disables it and `AE_MCP_READONLY=1` limits project mutation. Native writes require inspection of the exact project first. Requests and responses are exchanged through a per-user temp mailbox; the runtime warns when a custom mailbox is too broadly writable. Render exports and saved AEPs are written to local user-chosen paths. Batches are undo-grouped but do not roll back on failure; after a timeout, the actual AE state must be inspected before retry.

The expected setup includes an installed, licensed AE copy, Node 24+, AE's scripting-file-access preference and, on macOS, Automation permission for the host. AFT-5's offline doctor reports prerequisite discovery but does not claim a permission grant. Local install, first-use and recovery work has development-Mac evidence; a genuinely separate-machine journey and final public Git installation are still open. The tested native host is macOS 26.6.2 on arm64 with AE 26.5x89; broader compatibility is not asserted. The source has an explicit read-only setting and an opt-out for `eval.run`, but ordinary installation retains project and file read/write/delete capabilities. The per-user mailbox uses one request/response file per call; a consumed write with a missing response is reported as possibly executed and must be inspected before retry.

## Current official distribution constraints

OpenAI's [plugin packaging guide](https://developers.openai.com/plugins/build/plugins) says public plugin publication goes to the universal directory, while local/repo marketplaces are separate sources. It supports Git-backed marketplace entries and CLI addition, and still accepts this package's `.codex-plugin/plugin.json` compatibility layout. It identifies root `plugin.json` plus `mcp.json` as the portable form, a packaging task for AFT-21 rather than evidence that this local MCP is eligible for directory review.

The same guide says a locally running MCP should use a public HTTPS endpoint for the ordinary public submission path or reach an OpenAI contact for local MCP support. The [submission conversion guide](https://developers.openai.com/plugins/guides/submit-claude-plugin) calls for contacting an OpenAI partner before submitting a plugin whose core value requires local execution, arbitrary local file access, hardware/application access or offline operation; product-specific review may be needed. The [MCP server guide](https://developers.openai.com/plugins/build/mcp-server) requires a stable public HTTPS endpoint for standard public submission and says a temporary tunnel or local endpoint is insufficient. These are current documented rules, not a confirmation that OpenAI has accepted this specific plugin.

An HTTPS server alone cannot directly control a customer's local AE instance. A remote companion would require a new authenticated, user-scoped device bridge and a different data-flow/security design. That is a separate product architecture decision with significant build and operations cost; no such bridge exists in this package.
