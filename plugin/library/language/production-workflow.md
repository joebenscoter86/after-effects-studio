# Portable production workflow

This process uses the user's request and assets plus the plugin. It does not expect Joe's Content checkout, personal fonts, footage or a preexisting MASTER rig.

## 1. Orient and specify

Read `motion-language` and inspect the AE host/project. Identify the target project, format, duration, message, evidence, narration, available assets and reference. Infer ordinary choices from the request. Ask only for information that changes the result or an asset that is genuinely required. Never close or save over unrelated unsaved work.

For an empty project, create the needed compositions and native layers explicitly. Don't call house rig functions assuming JOE, BOARD, CAMERA or GRAIN exists. `motion-jsx` is portable; `house-jsx` and `joeb-motion-jsx` are optional integrations with declared dependencies.

## 2. Establish the visual operation

Use the brief template. Define start/action/payoff for each section, the star, material treatment, typography roles, factual sources, camera purpose, frame timings and hand-off. Read the actual available assets before naming them. The detailed language is the default foundation even when the requested look is completely different from JoeB.

If the user provides a visual reference, measure a relevant short shot using `reference-study`. Transfer its mechanism into an original design. Use references and examples to make decisions, not as decoration in a moodboard.

## 3. Test the hard passage and an ordinary beat

For a new look, compose start/action/payoff poses and build a small representative native section. Include the difficult hand-off and a normal proof/explanation beat. This checks whether the visual system sustains more than one impressive moment. When the user asks for iterative direction, show this section for feedback. When authorized to complete autonomously, self-review and continue; don't insert an unrequested approval stop.

## 4. Build in coherent sections

Create versioned scripts with scene ownership prefixes. Preserve approved layers/assets and rebuild only the intended sections. Parent at rest, set coordinate spaces, create actual background layers, and inspect text bounds. Fetch schemas from the native operation catalog; legacy cloud bridge limitations are not the native API contract.

Record what actually changed and compare the live project to that expectation. Script failures and timeouts mean the visual state is uncertain. Inspect before retrying. Do not render a stale pre-build project and mistake it for the new version.

## 5. Review and correct

Apply `failure-atlas` and `quality`. Inspect the native render across start, action, maximum overlap, hold and transition. Use a contact sheet for temporal coverage and full-size frames for edges/type. Review denser frame strips around fast hand-offs. Use a playable clip for speed, sound, camera rhythm and VO sync. If playback is unavailable, explicitly leave those checks open.

Name the weak part and fix its cause. If the idea is wrong, revise the brief. If a rendered middle pose fails, fix the trajectory/stack, not only the endpoint. Technical pass is not taste approval. Don't claim a user has approved something because automated checks passed.

## 6. Deliver editability and a verified file

Save intentionally, gather referenced assets, retain native editable type/shapes/keyframes, and export the requested format. Use an existing suitable render template or discover actual installed options. Verify output metadata and complete decode. Check the delivered copy matches the verified export when copying elsewhere. Report remaining dependencies and unperformed checks.

## 7. Preserve reusable discoveries

In the project, record the accepted operation, exact timings/curves, assets, implementation pitfalls and evidence. Distinguish proven user preference from a hypothesis. A fix becomes a reusable recipe when it works across builds or the user explicitly adopts it. Don't silently mutate global memory or the installed plugin during ordinary production.
