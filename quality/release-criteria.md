# Public v1 release criteria

Current state: incomplete. The initial scaffold and previous smoke tests do not satisfy a full release.

- Clean installation: one genuinely separate, personally owned or expressly authorized machine with no Content checkout or preconfigured plugin reaches its first editable comp through documented setup. Joe's company-managed Mac is excluded by D-011. Joe may operate an eligible machine; recruiting an outside technical tester is not a prerequisite. Verify declared runtime and permission requirements and record every manual intervention. A Joe-operated run proves package portability, not ease of use for an ordinary creator.
- Supported platforms: each advertised OS/AE combination has actual installation, creation, revision and export evidence. Only local macOS/AE26.5 native checks exist so far.
- Visual outcomes: three distinct complete examples (type identity, causal explainer and transparently fictional original-art concept product), each with an ordinary beat, difficult transition, meaningful revision, real rendered review and full-speed playback. The generated product image is fixed input with recorded provenance, not evidence that a real commercial product exists.
- Capability boundary: after the representative examples, execute one substantially harder, rights-cleared real-world brief with a documented difficulty target, meaningful late revision, editable handoff and complete visual review. Record runtime limits, manual work and visual failures as well as successes; do not call a partial result a pass. The [AFT-27 first-party film and late revision](reports/2026-10-10-capability-probe/revision-report-v2.md) passed their bounded creative/control challenge with Joe's acceptance. AFT-29's render false-success defect was subsequently resolved and [tested through the refreshed installed candidate](reports/2026-10-11-render-completion/report.md); neither result claims a universal creative ceiling.
- Editable delivery: open the delivered AEP, verify linked assets and native editable structure, verify movie metadata and complete decode, and match delivered copies.
- Recovery: test absent fonts/media, closed/busy AE and uncertain execution. D-013 replaces waiting for a natural timeout with a controlled test-only response fault after a harmless owned write, paired with successful dispatch and real native-state inspection. Prove conservative uncertainty handling, no duplicate replay, safe late-response/lock handling and unrelated-project preservation. Never induce an AE hang or ship the fault harness. AFT-9 and AFT-18 may run independently; both must pass before AFT-23.
- Lifecycle: AFT-33 exercises versioned update, removal and restoration of a known-good package in an owned installation context. User AEPs/exports and unrelated host settings survive. Document and test actual host recovery if direct rollback is unavailable.
- Portable craft: a fresh agent session reads only packaged guidance and applies it to multiple styles without personal rig/assets. The prior two-prompt authoring exercise is partial evidence.
- Package: all manifests/resources validate; notices and chosen licensing terms are present; no private credentials or personal media are shipped; public metadata and support links are real.
- Distribution: D-006/D-013 select public Git-backed Codex distribution with guided install. AFT-31/AFT-20 prepare reviewed source/content; AFT-32 publishes public distribution infrastructure after specific authorization (which exposes downloadable source/catalog), then AFT-34 rehearses the actual public source before stable-release review. AFT-24 publishes the approved stable release and AFT-25 verifies what users receive. A local kit alone does not prove the public route. Universal-directory eligibility/preparation/submission (AFT-30/AFT-35/AFT-36) are a separate track and never block Codex launch.

First-use clarity is a separate product check: the instructions should not require Git commands, source builds or developer dependencies from the user. Observe any willing creator following the guide when one is available and log where they get stuck; do not label a developer-operated installation as independent user validation. This observation can inform onboarding before or after the first public release without blocking engineering or the one-machine portability gate.

For each result record scenario, date, package hash/version, host, inputs, exact actions, output paths, checks performed, failures/corrections and remaining limits. Put each run in reports/YYYY-MM-DD-topic/. Keep heavy outputs in the matching renders/ folder.
